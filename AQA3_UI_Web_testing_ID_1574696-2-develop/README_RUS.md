## Глава 3

### 3.1. Про тестирование Web UI

Тестирование веб-интерфейсов — это процесс проверки того, насколько удобно и правильно пользователю взаимодействовать с приложением. Корректно ли отображаются элементы? Работают ли кнопки, формы и навигация? Если зайти с другого браузера, сохраняется ли функциональность и разрешения экранов? Чаще всего в итоге это будет е2е-тестирование или же, другими словами, тестирование веб-сценариев.

Классический подход начинается с ручного тестирования: QA-инженер вручную кликает, вводит данные, проверяет сценарии и фиксирует баги. Но чем сложнее проект, тем больше времени уходит на однотипные проверки, особенно при регрессионном тестировании. И тогда на помощь приходит автоматизация.

Автоматизированное тестирование Web UI строится на симуляции действий пользователя через код: открытие страниц, заполнение полей, кликание и проверка, все ли работает как надо.

Однако есть нюансы: скорость загрузки страниц, динамическое изменение DOM, кросс-браузерная совместимость могут повлиять на стабильность таких тестов.

Чтобы минимизировать риски или упростить работу, QA-инженеры используют специализированные инструменты:

- Фреймворки (в этом проекте ты рассмотришь Selenide) — они упрощают взаимодействие с браузером и элементами страницы.
- Синтаксис Gherkin (в этом проекте ты рассмотришь Cucumber) — он превращает тест-кейсы в понятные сценарии на естественном языке. Данный инструмент еще не так часто используется, как остальные, но его популярность быстро растет. Поэтому умение им пользоваться станет для тебя значительным преимуществом при подаче на любую вакансию!
- Системы отчетности (в этом проекте ты рассмотришь Allure) — они делают результаты прогонов автотестов наглядными (с выделенными ошибками и детализацией).

Таким образом, автоматизация часто возникает не с целью замены ручного тестирования, а для его дополнения: забирает на себя рутину и позволяет сосредоточиться на сложных кейсах.

А чтобы такой подход работал эффективно, нужно не только уметь программировать, но и выбирать подходящие инструменты под задачи проекта. Об этом — дальше.

### 3.2. Selenide

**Selenide** — это фреймворк для автоматизации тестирования веб-интерфейсов, построенный на базе Selenium WebDriver. Его ключевая цель — сделать написание UI-тестов максимально простым, лаконичным и стабильным.

Selenide забирает на себя рутинные задачи: управление браузером, таймауты, обработку исключений, а ты можешь сосредоточиться на логике тестов, а не на технических деталях.

**Основные принципы работы**

1. **Автоматическое управление браузером**

Selenide самостоятельно запускает и закрывает браузер (по умолчанию — Chrome). Для инициализации достаточно указать конфигурацию в коде:

```java
Configuration.browser = "firefox"; // выбор браузера
Configuration.headless = true;     // режим без графического интерфейса
```

2. **Поиск элементов**

Элементы страницы находятся через CSS- или XPath-селекторы с помощью метода $:

3. **Автоматические ожидания**

```java
$(By.id("login-button")).click();                      // поиск по ID
$("input[name='email']").setValue("test@mail.com");    // CSS-селектор
```

Selenide ждет появления элемента, его видимости или кликабельности (до 4 секунд по умолчанию), что избавляет от ручных `Thread.sleep()` и `WebDriverWait`.

4. **Проверки (Assertions)**

Встроенные методы для валидации:

```java
$(".title").shouldHave(text("Welcome")); // проверка текста
$("#submit-btn").shouldBe(disabled);     // проверка состояния элемента
```

**Преимущества Selenide:**

- Лаконичный синтаксис: написание тестов требует в 2–3 раза меньше кода, чем на чистом Selenium. 
- Стабильность: встроенные ожидания и обработка исключений снижают количество «ложных падений».
- Интеграция: совместим с JUnit, TestNG, Cucumber, Allure и другими инструментами. 
- Документация: подробные руководства и примеры на официальном сайте.

### 3.3. Паттерн Page Object 

**Page Object Pattern** — это подход, при котором каждая страница веб-приложения описывается отдельным классом. 

Внутри такого класса хранятся локаторы элементов (например, поля ввода, кнопки) и методы для взаимодействия с ними (клики, ввод данных). Это снижает дублирование кода, упрощает поддержку тестов и делает их читаемыми: если изменится интерфейс, правки вносятся только в соответствующий класс, а не во все тесты.

**Плюсы для автоматизации:**

- Тесты становятся лаконичными: вместо серии Selenide-команд вызываются методы вроде `loginPage.enterCredentials()`.
- Логика работы со страницей инкапсулирована, что упрощает совместную работу команды.
- Интеграция с Cucumber и Allure делает сценарии прозрачными, а отчеты — детализированными.

Page Object — это фундамент для стабильных и масштабируемых автотестов.

### 3.4. Cucumber

**Cucumber** — это инструмент для BDD (Behavior-Driven Development), который позволяет описывать тесты в формате, понятном всем участникам команды (QA, разработчикам, менеджерам).

Тесты пишутся на естественном языке в формате feature-файлов с использованием ключевых слов:

```java
# language: ru
Функция: Авторизация пользователя
Сценарий: Успешный вход
Дано Пользователь на странице логина
Когда Он вводит логин "admin" и пароль "qwerty123"
Тогда Открывается личный кабинет
```

При этом в коде это все отражается следующим образом:

```java
@Когда("Пользователь на странице логина")

public void openLoginPage() {
   open("/login");
}

@Тогда("Он вводит логин {string} и пароль {string}")

public void enterCredentials(String login, String password) {
   $("#username").setValue(login);
   $("#password").setValue(password).pressEnter();
}
```

**Зачем это нужно?**

- Единый язык: тесты становятся документацией, которую понимает вся команда.
- Переиспользование шагов: один шаг (например, «логин пользователя») можно применять во множестве сценариев.

### 3.5. Allure

**Allure** — это фреймворк для создания интерактивных и детализированных отчетов о прогоне автотестов.

Он превращает сырые данные (логи, скриншоты, метрики) в наглядные дашборды, которые помогают быстро находить причины падений и анализировать стабильность тестов.

**Как это работает?**

Allure подключается к проекту через зависимости (Maven/Gradle) и аннотации. Например, с Selenide он автоматически фиксирует скриншоты при падении тестов, а с Cucumber — отображает сценарии в формате Gherkin.

Можно дополнять контекст каждого отчета следующими вещами:

- скриншотами при ошибках (Selenide делает это автоматически),
- логами запросов и ответов,
- метками (тегами, severity, epic) для группировки тестов.

Пример аннотации в коде:

```java
@Step("Ввести логин {login}")

public void enterLogin(String login) {
   $("#username").setValue(login);
}
```

После прогона тестов отчет создается командой *allure serve allure-results*.

**Что отражается в отчете:**

- графики: общая статистика по passed/failed/skipped тестам;
- дерево сценариев: группировка по фичам, эпикам, тегам;
- шаги теста: детализация каждого шага (благодаря @Step);
- прикрепленные данные: скриншоты, логи, видео (если настроено).

**Преимущества Allure:**

- Понятность: даже новичок разберется, где и почему упал тест.
- Гибкость: поддерживает все популярные фреймворки (Selenide, Cucumber, JUnit).
- Простота: отчет генерируется одной командой в терминале.

**Итог**

Связка Selenide + Cucumber + Allure покрывает весь цикл автоматизации:

1. Selenide — стабильные и лаконичные тесты;
1. Cucumber — сценарии на языке бизнеса;
1. Allure — наглядная аналитика результатов.

Теперь давай приступать к практике и писать автотесты, которые будут не только работать, но и «говорить» на понятном всем языке! 🚀

**Критически важное правило:**
1. Сначала выполни задания вручную — это обязательное условие. Опытные специалисты делегируют ИИ задачи, только после того, как сами знают ее решение - ИИ привлекают, чтобы помочь оптимизировать или сгенерировать похожие. Результаты, полученные вручную помечай, например, manual-solution.

- В реальной работе ИИ ошибается постоянно - может сгенерировать красивый, но нерабочий код - проверяй все результаты выдач и исправляй при необходимости.
